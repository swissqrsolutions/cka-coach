

==================== PAGE 1 · ImagePullBackOff ====================
EXAM QUESTION:
In namespace `app`, the pod of deployment `api` is not Running. Find the cause and fix it so the pod reaches Running. Do not delete the deployment.
WRITE DOWN: namespace = `app` · deployment = `api` · do NOT delete the deployment

WORDS YOU NEED:
- Image = the packaged app, stored in a registry. Written as name:tag, for example nginx:1.27. The tag is the version.

- Deployment = the object that creates and re-creates the pod. It is the pod&#39;s owner.

- ImagePullBackOff = the node tried to download the image, failed, and now waits longer and longer between retries.

SPOT THE PATTERN: Pod not Running → read Events → fix the owner (Deployment)
  "is not Running" → Look at STATUS, then read Events with describe
  "Do not delete the deployment" → Fix it in place: k set image / k edit deploy
  "so the pod reaches Running" → Done only when the NEW pod shows 1/1 Running

IN PLAIN WORDS:
Something stops the pod from starting. You do not know what yet. Kubernetes knows, and wrote it into the pod&#39;s Events. Read it, then fix it in the deployment.

SET UP IN KILLERCODA:
k delete ns app --ignore-not-found
k create ns app
k create deploy api --image=nginx:doesnotexist -n app

SOLVE IT, STEP BY STEP:
0. Start of every question: in Killercoda just k get nodes (exam: ssh line first)
1. Step 1. See the status
   $ k get pods -n app
   You see:
   YOU SEE: NAME                   READY   STATUS             RESTARTS   AGE
            api-697db8cc78-hgvdr   0/1     ImagePullBackOff   0          60s
   | 
   
    | Column
    | Value
    | Meaning
   
    | READY
    | 0/1
    | the pod should have 1 container; 0 are ready
   
    | STATUS
    | ImagePullBackOff
    | the image cannot be downloaded
   
    | RESTARTS
    | 0
    | the container never started, so nothing restarted
   Copy the pod name.
2. Step 2. Ask Kubernetes why
   $ k describe pod <pod-name> -n app
   Read two places:
   1. Near the top, under Containers: the first indented word is the container name. Here: nginx. Write it down. 2. At the bottom, under Events: you see Failed to pull image "nginx:doesnotexist" ... not found.
   Cause found: the image nginx exists, but the tag doesnotexist does not.
3. Step 3. Fix the image in the deployment
   $ k set image deploy/api nginx=nginx:1.27 -n app
   How to read it: k set image deploy/<deployment> <container-name>=<new-image>. The left side of = is the CONTAINER name from step 2, not the deployment name.
   If the question does not give a tag, use the plain image name: nginx=nginx.
4. Closing routine
   $ k rollout status deploy/api -n app
   $ k get pods -n app
   You want a pod with a NEW name showing 1/1 Running. The new name is correct: the deployment replaced the broken pod.

IF SOMETHING GOES WRONG:
| 

 | You see
 | Cause
 | Fix

 | error: unable to find container named "api"
 | you used the deployment name on the left of =
 | use the container name from describe

 | still ImagePullBackOff
 | the new image name or tag also has a typo
 | k describe pod again, read Events, run set image again

 | No resources found
 | you forgot -n app
 | add it

TRAPS TO AVOID:
- Using the deployment name (api) as the container name in set image — the container is nginx
- Forgetting -n app → 'No resources found'
- Fixing the pod instead of the deployment — the deployment recreates the broken pod

VERIFY AGAINST THE QUESTION:
- pod reaches Running: $ k get pods -n app  → must see: new api-… pod 1/1 Running
- deployment not deleted: $ k get deploy api -n app  → must see: api 1/1

MEMORISE (fast version, target 2 min):
k get pods -n app
k describe pod <pod> -n app   # Events: ImagePullBackOff, bad tag
k set image deploy/api nginx=nginx:1.27 -n app
k rollout status deploy/api -n app


==================== PAGE 2 · CrashLoopBackOff ====================
EXAM QUESTION:
In namespace `app`, the pod of deployment `api` keeps restarting. Find the cause and fix it so the pod stays Running. Do not delete the deployment. The container should run `sleep 3600`.
WRITE DOWN: namespace = `app` · deployment = `api` · correct command = `sleep 3600`

WORDS YOU NEED:
- Command = what the container runs when it starts. A container lives only as long as its command keeps running.

- Exit code = the number a command returns when it stops. 0 = finished OK. Anything else = stopped with an error.

- CrashLoopBackOff = the image downloaded fine, the container started, then stopped. Kubernetes restarts it, it stops again. Kubernetes waits longer between each retry.

SPOT THE PATTERN: Pod CrashLoopBackOff → logs --previous → fix command in Deployment
  "keeps restarting" → CrashLoopBackOff: the container starts then exits; read logs --previous
  "Do not delete the deployment" → Fix the pod template with k edit deploy
  "The container should run" → The command in the spec is wrong; set it to sleep 3600

IN PLAIN WORDS:
The container starts and stops in a loop. Find out WHY it stops. The reason is in one of two places: what the container printed before it stopped (logs), or the command it was told to run (describe).

SET UP IN KILLERCODA:
k delete ns app --ignore-not-found
k create ns app
k create deploy api --image=busybox:1.36 -n app -- sh -c "exit 1"

SOLVE IT, STEP BY STEP:
0. Start of every question: in Killercoda just k get nodes (exam: ssh line first)
1. Step 1. See the status
   $ k get pods -n app
   You see:
   YOU SEE: NAME                   READY   STATUS             RESTARTS      AGE
            api-5d9c7b6f4-x2x9k    0/1     CrashLoopBackOff   3 (20s ago)   70s
   RESTARTS is going UP. That is the difference from question 1: the container does start, then stops.
2. Step 2. Read what the stopped container printed
   $ k logs <pod-name> -n app --previous
   --previous = show the output of the container that just stopped, not the new one.
   Here it prints nothing, because exit 1 prints nothing. In the exam you often see a real message here, for example file not found or missing variable. That message is the cause.
3. Step 3. Read the command and the exit code
   $ k describe pod <pod-name> -n app
   Find these lines:
   YOU SEE:     Command:
                  sh
                  -c
                  exit 1
                Last State:     Terminated
                  Reason:       Error
                  Exit Code:    1
   Cause found: the command is exit 1. It stops at once with an error.
4. Step 4. Fix the command in the deployment
   $ k edit deploy api -n app
   This opens the deployment in vim. Type /exit 1 and press Enter. The cursor jumps to:
   YOU SEE:       - command:
                    - sh
                    - -c
                    - exit 1
   Press i, change exit 1 to sleep 3600. Press Esc, type :wq, press Enter.
   You see deployment.apps/api edited.
5. Closing routine
   $ k get pods -n app
   You want 1/1 Running and RESTARTS 0. Wait 20 seconds and run it again: RESTARTS must stay 0.

IF SOMETHING GOES WRONG:
The steps are identical. Only the message and the fix change.

 | 

 | What you read in steps 2 and 3
 | Cause
 | Fix

 | Reason: OOMKilled
 | the memory limit is too small
 | k set resources deploy api -n app --limits=memory=256Mi

 | STATUS CreateContainerConfigError, Events: configmap "x" not found
 | the ConfigMap or Secret does not exist
 | create it (k create cm x --from-literal=KEY=VALUE -n app) or fix its name with k edit deploy

 | Events: Liveness probe failed
 | the probe checks the wrong port or path
 | k edit deploy api -n app, fix the port under livenessProbe:

 | logs show an error about a wrong argument
 | bad args:
 | k edit deploy api -n app, fix args:

TRAPS TO AVOID:
- Reading k logs without --previous (the new container may have no output yet)
- Editing the pod instead of the deployment
- Breaking YAML indentation in the command list

VERIFY AGAINST THE QUESTION:
- pod stays Running: $ k get pods -n app  → must see: 1/1 Running, RESTARTS stays 0 for the new pod
- container runs sleep 3600: $ k get deploy api -n app -o yaml | grep -A3 command  → must see: sleep 3600

MEMORISE (fast version, target 3 min):
k get pods -n app
k logs <pod> -n app --previous
k describe pod <pod> -n app
k edit deploy api -n app   # exit 1 → sleep 3600
k get pods -n app


==================== PAGE 3 · Pending pod ====================
EXAM QUESTION:
In namespace `app`, a pod of deployment `api` is stuck in Pending. Find the cause and fix it. The container needs `100m` CPU.
WRITE DOWN: namespace = `app` · deployment = `api` · correct CPU request = `100m`

WORDS YOU NEED:
- Scheduler = the part of Kubernetes that picks a node for each new pod.

- Pending = the pod exists, but no node has accepted it yet.

- Request = how much CPU and memory a pod reserves. CPU is written in millicores: 1000m = 1 CPU, 100m = one tenth of a CPU. A plain 100 means 100 whole CPUs.

SPOT THE PATTERN: Pod Pending → describe Events → lower resource requests
  "stuck in Pending" → The scheduler cannot place it: read Events (Insufficient cpu)
  "The container needs" → Set the CPU request to exactly 100m on the deployment

IN PLAIN WORDS:
The scheduler looked at every node and said no to all of them. It wrote its reason into the pod&#39;s Events. Read the reason, remove the obstacle.

SET UP IN KILLERCODA:
k delete ns app --ignore-not-found
k create ns app
k create deploy api --image=nginx:1.27 -n app
k set resources deploy api -n app --requests=cpu=100

SOLVE IT, STEP BY STEP:
0. Start of every question: in Killercoda just k get nodes (exam: ssh line first)
1. Step 1. See the status
   $ k get pods -n app
   You see one pod Pending. You may also see an older pod still Running: the deployment keeps the old pod until the new one works. Copy the name of the PENDING pod.
2. Step 2. Read the scheduler's reason
   $ k describe pod <pending-pod-name> -n app
   At the bottom, under Events:
   YOU SEE: Warning  FailedScheduling  ...  0/2 nodes are available: 2 Insufficient cpu.
   How to read it: "0 of 2 nodes can take this pod. Both do not have enough CPU."
   Look higher up in the same output, under Requests: → cpu: 100. That is 100 whole CPUs. No node has that.
3. Step 3. Fix the request in the deployment
   $ k set resources deploy api -n app --requests=cpu=100m
4. Closing routine
   $ k get pods -n app
   You want 1/1 Running, and no Pending pod left.

IF SOMETHING GOES WRONG:
The Events line always names the cause. Match it:

 | 

 | Events says
 | Cause
 | Fix

 | Insufficient cpu or Insufficient memory
 | the request is too big
 | k set resources deploy api -n app --requests=cpu=100m,memory=128Mi

 | had untolerated taint {key: value}
 | the node has a taint the pod does not tolerate
 | remove the taint: k taint node node01 key=value:NoSchedule- (or add a toleration, question 36)

 | didn&#39;t match Pod&#39;s node affinity/selector
 | the pod asks for a node label that no node has
 | k edit deploy api -n app and fix nodeSelector:, or k label node node01 key=value

 | unbound immediate PersistentVolumeClaims
 | its PVC is not Bound
 | fix the PVC (questions 38 and 40)

 | Events is empty (<none>)
 | the scheduler itself is not running
 | question 9

TRAPS TO AVOID:
- Setting --limits instead of --requests
- Editing the pod instead of deployment api
- Not waiting for the old Pending pod to be replaced

VERIFY AGAINST THE QUESTION:
- pod no longer Pending: $ k get pods -n app  → must see: new pod 1/1 Running
- request is 100m: $ k get deploy api -n app -o jsonpath='{..resources}'  → must see: "requests":{"cpu":"100m"}

MEMORISE (fast version, target 2 min):
k get pods -n app
k describe pod <pod> -n app   # Insufficient cpu
k set resources deploy api -n app --requests=cpu=100m
k get pods -n app


==================== PAGE 4 · Node NotReady: kubelet stopped ====================
EXAM QUESTION:
Node `node01` is in state NotReady. Find the cause and bring the node back to Ready. The fix must survive a reboot. Do not reboot the node.
WRITE DOWN: node = `node01` · must survive reboot (so: `enable`) · no reboot

WORDS YOU NEED:
- kubelet = a program that runs on every node. It starts the containers, and every few seconds it reports "this node is alive" to the control plane.

- NotReady = the control plane has not heard from that node&#39;s kubelet for about 40 seconds.

- systemctl = the Linux command that starts, stops and checks services. kubelet is a Linux service, not a pod. So kubectl cannot start it. You must log in to the node.

SPOT THE PATTERN: Node NotReady → ssh → kubelet stopped → enable --now
  "is in state NotReady" → Kubelet on that node is not reporting: ssh in and check systemctl
  "The fix must survive a reboot" → Use systemctl enable (not only start)
  "Do not reboot the node" → Start the service by hand: enable --now

IN PLAIN WORDS:
The kubelet on node01 is not reporting. Log in to node01, check the kubelet service, start it.

SET UP IN KILLERCODA:
ssh node01 "systemctl stop kubelet"

SOLVE IT, STEP BY STEP:
0. Start of every question: in Killercoda just k get nodes (exam: ssh line first)
1. Step 1. Get the hint from the control plane
   $ k describe node node01
   Find the Conditions: table. You see Unknown and the message Kubelet stopped posting node status.
   That sentence tells you: the problem is the kubelet, on that node.
2. Step 2. Log in to the node
   $ ssh node01
   The prompt changes to root@node01. Always look at the prompt before you type.
3. Step 3. Check the kubelet service
   $ systemctl status kubelet
   You see:
   YOU SEE:      Active: inactive (dead) since ...
   inactive (dead) = the service is stopped. If the screen does not return to the prompt, press q.
4. Step 4. Start it
   $ systemctl enable --now kubelet
   - --now = start it immediately - enable = also start it after every reboot (the question asked for this)
   Check:
   YOU SEE: systemctl status kubelet
   You want Active: active (running). Press q.
5. Step 5. Leave the node
   $ exit
   The prompt is root@controlplane again.
6. Closing routine
   $ k get nodes
   You want node01   Ready. It can take 30 seconds. Run it again if needed.

IF SOMETHING GOES WRONG:
| 

 | You see
 | Cause
 | Fix

 | The connection to the server localhost:8080 was refused
 | you ran kubectl ON node01. kubectl is only set up on the control plane.
 | type exit, run it again

 | after starting: Active: activating (auto-restart)
 | the kubelet is misconfigured, not just stopped
 | question 5

 | kubelet is active (running) but the node stays NotReady
 | the container runtime is stopped
 | on the node: systemctl enable --now containerd

TRAPS TO AVOID:
- systemctl start only — not enabled, lost after reboot
- Running systemctl on the control plane instead of node01
- Forgetting to exit back before k get nodes

VERIFY AGAINST THE QUESTION:
- node Ready: $ k get nodes  → must see: node01 Ready
- survives reboot: $ ssh node01 systemctl is-enabled kubelet  → must see: enabled

MEMORISE (fast version, target 2 min):
k describe node node01   # Kubelet stopped posting status
ssh node01
systemctl status kubelet
systemctl enable --now kubelet
exit; k get nodes


==================== PAGE 5 · Node NotReady: kubelet misconfigured ====================
EXAM QUESTION:
Node `node01` is in state NotReady. Find the cause and bring the node back to Ready. Do not reboot the node.
WRITE DOWN: node = `node01` · no reboot

WORDS YOU NEED:
- Service file = a text file that tells Linux how to start a service. The line ExecStart= holds the path of the program to run.

- journalctl = the command that shows a service&#39;s log. It tells you WHY a service fails.

- daemon-reload = tells Linux "I changed a service file, read it again". Without it, Linux keeps using the old version.

SPOT THE PATTERN: Node NotReady → kubelet fails → fix service file path
  "is in state NotReady" → ssh to node01, check kubelet status and journal
  "Do not reboot the node" → After editing the unit: daemon-reload + restart kubelet

IN PLAIN WORDS:
The wording is the same as question 4. You only find out on the node that this one is harder: the kubelet is not just stopped, it cannot start. Something in its configuration is wrong. journalctl tells you what.

SET UP IN KILLERCODA:
ssh node01 "sed -i 's#/usr/bin/kubelet#/usr/local/bin/kubelet#' /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf && systemctl daemon-reload && systemctl restart kubelet"

SOLVE IT, STEP BY STEP:
0. Start of every question: in Killercoda just k get nodes (exam: ssh line first)
1. Step 1. Log in to the node and check the service
   $ ssh node01
   $ systemctl status kubelet
   You see:
   YOU SEE:      Active: activating (auto-restart) (Result: exit-code)
                Process: ... ExecStart=/usr/local/bin/kubelet ... (code=exited, status=203/EXEC)
   | 
   
    | You see
    | Meaning
   
    | inactive (dead)
    | just stopped → question 4
   
    | activating (auto-restart)
    | tries to start, fails, tries again → it is misconfigured → this question
   Press q.
2. Step 2. Read WHY it fails
   $ journalctl -u kubelet -n 30 --no-pager
   - -u kubelet = only this service - -n 30 = the last 30 lines - --no-pager = print it, do not open a viewer
   You see:
   YOU SEE: kubelet.service: Failed to locate executable /usr/local/bin/kubelet: No such file or directory
   Cause found: the service file points to a program path that does not exist.
3. Step 3. Find the correct path
   $ which kubelet
   Answer: /usr/bin/kubelet
4. Step 4. Find which file holds the wrong path
   $ systemctl cat kubelet
   It prints every file of the service, each with its path in a # line on top. Look for the ExecStart= line with the wrong path. The # line above that block names the file:
   YOU SEE: # /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf
5. Step 5. Fix the file
   $ vim /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf
   Type /local and press Enter. Change /usr/local/bin/kubelet to /usr/bin/kubelet. Save with Esc, :wq.
6. Step 6. Reload, restart, check
   $ systemctl daemon-reload
   $ systemctl restart kubelet
   $ systemctl status kubelet
   You want Active: active (running). Press q.
7. Step 7. Leave the node
   $ exit
8. Closing routine
   $ k get nodes
   You want node01   Ready (up to 30 seconds).

IF SOMETHING GOES WRONG:
journalctl always names the problem. These are the files where the fix goes:

 | 

 | journalctl says
 | File to fix
 | Then

 | Failed to locate executable ...
 | /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf (the ExecStart= line)
 | daemon-reload + restart

 | unknown flag: --xyz
 | /var/lib/kubelet/kubeadm-flags.env
 | restart

 | failed to load kubelet config file or unable to load client CA file ...
 | /var/lib/kubelet/config.yaml (correct CA path: /etc/kubernetes/pki/ca.crt)
 | restart

 | dial tcp ...:6553: connection refused (wrong API server port)
 | /etc/kubernetes/kubelet.conf (correct port: 6443)
 | restart

daemon-reload is only needed after changing a file under /usr/lib/systemd/ or /etc/systemd/. Running it when not needed does no harm.

TRAPS TO AVOID:
- Forgetting systemctl daemon-reload after editing the unit file
- Editing the wrong file — use systemctl cat kubelet to find which file has ExecStart
- Only starting kubelet without fixing the bad /usr/local/bin path

VERIFY AGAINST THE QUESTION:
- kubelet running: $ systemctl status kubelet  → must see: Active: active (running)
- node Ready: $ k get nodes  → must see: node01 Ready

MEMORISE (fast version, target 4 min):
ssh node01; systemctl status kubelet
journalctl -u kubelet -n 30 --no-pager
which kubelet; systemctl cat kubelet
vim /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf   # /usr/local/bin/kubelet → /usr/bin/kubelet
systemctl daemon-reload; systemctl restart kubelet


==================== PAGE 6 · Service has no endpoints ====================
EXAM QUESTION:
In namespace `web`, pod `client` cannot reach service `backend-svc` on port 80. The deployment `backend` is Running. Find and fix the issue. Do not delete or recreate the service.
WRITE DOWN: namespace = `web` · service = `backend-svc` · deployment = `backend` · test pod = `client` · do NOT recreate the service

WORDS YOU NEED:
- Label = a key=value tag on an object, for example app=backend.

- Selector = a label written inside a Service. The Service sends traffic to every pod that carries that label.

- Endpoints = the list of pod IPs the Service found with its selector. Empty list = the Service found no pods = traffic goes nowhere.

SPOT THE PATTERN: Service unreachable → no endpoints → fix selector to match labels
  "cannot reach service" → Check k get endpoints first: empty = selector mismatch
  "is Running" → Pods are fine; the Service is the problem
  "Do not delete or recreate the service" → Change it in place: k set selector or k edit svc

IN PLAIN WORDS:
The pods are healthy. The Service exists. But the Service is not connected to the pods. Compare the Service&#39;s selector with the pods&#39; labels.

SET UP IN KILLERCODA:
k delete ns web --ignore-not-found
k create ns web
k create deploy backend --image=nginx:1.27 -n web
k create svc clusterip backend-svc --tcp=80:80 -n web
k run client --image=busybox:1.36 -n web -- sleep 3600

SOLVE IT, STEP BY STEP:
0. Start of every question: in Killercoda just k get nodes (exam: ssh line first)
1. Step 1. Does the Service have pods behind it?
   $ k get endpoints backend-svc -n web
   You see:
   YOU SEE: NAME          ENDPOINTS   AGE
            backend-svc   <none>      1m
   <none> = the Service found no pods. (A deprecation warning on this command is harmless.)
2. Step 2. What label is the Service looking for?
   $ k describe svc backend-svc -n web
   Find the line Selector:  app=backend-svc.
3. Step 3. What labels do the pods really carry?
   $ k get pods -n web --show-labels
   The backend pod shows app=backend,....
   app=backend-svc is not app=backend. That is the cause.
4. Step 4. Fix the selector on the Service
   $ k set selector svc backend-svc app=backend -n web
   This changes the existing Service. It is not recreated.
5. Closing routine
   $ k get endpoints backend-svc -n web
   You want an IP, for example 192.168.1.5:80.
   $ k exec client -n web -- wget -qO- -T 3 backend-svc
   You want the HTML that contains Welcome to nginx!. - -qO- = quiet, print the page to the screen. It is the capital letter O, not a zero. - -T 3 = give up after 3 seconds

IF SOMETHING GOES WRONG:
| 

 | You see
 | Cause
 | Fix

 | endpoints still <none>
 | typo in the label you set
 | compare again with --show-labels

 | endpoints still <none>, labels match
 | the pods are not Ready (READY 0/1)
 | fix the pods first

 | endpoints show an IP, wget still fails
 | the port is wrong
 | question 7

 | wget: invalid option -- &#39;0&#39;
 | you typed zero instead of capital O
 | -qO-

TRAPS TO AVOID:
- Relabelling the pods instead of fixing the service selector
- Copying the pod-template-hash label into the selector
- Testing with curl — busybox client has wget

VERIFY AGAINST THE QUESTION:
- service has endpoints: $ k get endpoints backend-svc -n web  → must see: pod IP(s):80
- client can reach it: $ k exec client -n web -- wget -qO- -T 3 backend-svc  → must see: Welcome to nginx!

MEMORISE (fast version, target 3 min):
k get endpoints backend-svc -n web
k describe svc backend-svc -n web   # Selector
k get pods -n web --show-labels
k set selector svc backend-svc app=backend -n web
k exec client -n web -- wget -qO- -T 3 backend-svc


==================== PAGE 7 · Service with the wrong targetPort ====================
EXAM QUESTION:
In namespace `web`, pod `client` cannot reach service `backend-svc` on port 80. The backend pods are Running and run nginx, which listens on port 80. Fix the issue without recreating the service.
WRITE DOWN: namespace = `web` · service = `backend-svc` · app listens on `80`

WORDS YOU NEED:
- port = the port of the Service. Clients call this one.

- targetPort = the port of the container. The Service forwards the traffic there. It must be the port the app really listens on (nginx: 80).

- nodePort = only for NodePort Services: a port (30000 to 32767) opened on every node.

SPOT THE PATTERN: Service has endpoints but no answer → fix targetPort
  "listens on port 80" → targetPort must be 80
  "without recreating the service" → k edit svc and change targetPort only

IN PLAIN WORDS:
Same symptom as question 6, different cause. The Service finds the pods, but forwards to a port where nothing listens.

SET UP IN KILLERCODA:
k delete ns web --ignore-not-found
k create ns web
k create deploy backend --image=nginx:1.27 -n web
k expose deploy backend --name=backend-svc --port=80 --target-port=8080 -n web
k run client --image=busybox:1.36 -n web -- sleep 3600

SOLVE IT, STEP BY STEP:
0. Start of every question: in Killercoda just k get nodes (exam: ssh line first)
1. Step 1. Does the Service have pods behind it?
   $ k get endpoints backend-svc -n web
   You see:
   YOU SEE: NAME          ENDPOINTS          AGE
            backend-svc   192.168.1.5:8080   1m
   There IS an IP, so the selector is fine. Now look at the number after the colon: 8080. The question said nginx listens on 80.
   The rule: - ENDPOINTS <none> → selector problem (question 6) - ENDPOINTS has an IP but no answer → port problem (this question)
2. Step 2. Confirm the symptom
   $ k exec client -n web -- wget -qO- -T 3 backend-svc
   You see Connection refused or download timed out.
3. Step 3. Fix the port on the Service
   $ k edit svc backend-svc -n web
   Type /targetPort and press Enter. You see:
   YOU SEE:   ports:
              - port: 80
                protocol: TCP
                targetPort: 8080
   Change 8080 to 80. Save with Esc, :wq.
4. Closing routine
   $ k get endpoints backend-svc -n web
   $ k exec client -n web -- wget -qO- -T 3 backend-svc
   You want the Welcome to nginx! page.

IF SOMETHING GOES WRONG:
| 

 | You see
 | Cause
 | Fix

 | you do not know the app&#39;s port
 | the question did not say
 | k describe pod <backend-pod> -n web, read Port: under Containers

 | wget works with the pod IP but not with the Service name
 | DNS problem
 | question 11

 | the question says clients use another port, e.g. 8080
 | then port: is wrong, not targetPort:
 | fix port: instead

TRAPS TO AVOID:
