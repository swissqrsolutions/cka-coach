

==================== PAGE 21 · kubeadm upgrade ====================
EXAM QUESTION:
Upgrade the control plane node to Kubernetes `1.35.2`. Then upgrade the worker node `node01` to the same version. Drain each node before upgrading it and make it schedulable again afterwards.
WRITE DOWN: target version = `1.35.2` · nodes = `controlplane`, `node01` · drain before, uncordon after

WORDS YOU NEED:
- kubeadm = the tool that installed the cluster. It also upgrades it.

- Three programs are upgraded on each machine: kubeadm (the tool), kubelet (the node agent), kubectl (the command line).

- drain / uncordon = drain moves the pods off a node and closes it for new pods. uncordon opens it again. You drain before the upgrade and uncordon after.

Do not memorise the commands. Follow the docs page line by line. Memorise only the order:

Copydrain → new kubeadm → kubeadm upgrade → new kubelet + kubectl → restart kubelet → uncordon

SPOT THE PATTERN: kubeadm upgrade: drain → kubeadm → kubelet → uncordon, per node
  "Upgrade the control plane node to Kubernetes `1.35.2`" → Control plane first: kubeadm upgrade apply v1.35.2
  "Then upgrade the worker node `node01`" → On node01: kubeadm upgrade node (not apply)
  "Drain each node before upgrading it and make it schedulable again afterwards" → k drain … --ignore-daemonsets before, k uncordon after

IN PLAIN WORDS:
Do the same 6-step routine twice: once on the control plane, once on the worker. Only ONE command differs between the two (step 3).

SET UP IN KILLERCODA:
(cannot be set up in a playground)

SOLVE IT, STEP BY STEP:
0. Start of every question: in Killercoda just k get nodes (exam: ssh line first)
1. Closing routine
   $ k get nodes
   You want VERSION v1.35.2 on both nodes, STATUS Ready, and NO SchedulingDisabled.

IF SOMETHING GOES WRONG:
| 

 | You see
 | Cause
 | Fix

 | SchedulingDisabled next to a node
 | you forgot uncordon
 | k uncordon <node>

 | k drain refuses: "cannot delete Pods with local storage"
 | missing flag
 | add --delete-emptydir-data

 | k drain refuses: pods "not managed by a controller"
 | a bare pod is on the node
 | add --force

 | Version &#39;1.35.2&#39; not found
 | you need the full text
 | copy it from apt-cache madison kubeadm

 | VERSION still old after the upgrade
 | the kubelet was not restarted
 | systemctl daemon-reload && systemctl restart kubelet

 | localhost:8080 was refused
 | you ran k drain / k uncordon on node01
 | exit first

TRAPS TO AVOID:
- Running kubeadm upgrade apply on the worker — workers use kubeadm upgrade node
- Forgetting apt-mark unhold/hold, so apt refuses to install
- Forgetting daemon-reload + restart kubelet, so VERSION stays old
- Running k drain/uncordon from node01 (no kubeconfig there) — run them on the control plane

VERIFY AGAINST THE QUESTION:
- both nodes on 1.35.2: $ k get nodes  → must see: VERSION v1.35.2 on controlplane and node01
- schedulable again: $ k get nodes  → must see: Ready, no SchedulingDisabled

MEMORISE (fast version, target 12 min):
k drain <node> --ignore-daemonsets --delete-emptydir-data
apt-mark unhold kubeadm; apt-get install -y kubeadm='1.35.2-*'; apt-mark hold kubeadm
kubeadm upgrade apply v1.35.2   # worker: kubeadm upgrade node
apt-mark unhold kubelet kubectl; apt-get install -y kubelet='1.35.2-*' kubectl='1.35.2-*'; apt-mark hold kubelet kubectl
systemctl daemon-reload; systemctl restart kubelet
k uncordon <node>


==================== PAGE 22 · etcd backup and restore (lower priority) ====================
EXAM QUESTION:
1. Create a snapshot of etcd, which runs at `https://127.0.0.1:2379`, and save it to `/opt/etcd-backup.db`.
2. Restore the snapshot into the directory `/var/lib/etcd-restored` and configure etcd to use it.
WRITE DOWN: endpoint = `https://127.0.0.1:2379` · backup file = `/opt/etcd-backup.db` · restore folder = `/var/lib/etcd-restored`

WORDS YOU NEED:
- etcd = the database where the cluster stores every object. It runs as a static pod from /etc/kubernetes/manifests/etcd.yaml.

- Snapshot = a backup file of that database. Made with etcdctl snapshot save.

- Restore = unpack a snapshot into a NEW folder, then tell etcd to use that folder.

etcd only accepts connections that show three certificate files. Their paths are written in etcd.yaml.

SPOT THE PATTERN: etcd snapshot save (with certs) + restore + repoint hostPath
  "which runs at `https://127.0.0.1:2379`" → --endpoints=https://127.0.0.1:2379 plus cacert/cert/key from etcd.yaml
  "save it to `/opt/etcd-backup.db`" → etcdctl snapshot save /opt/etcd-backup.db
  "configure etcd to use it" → In etcd.yaml change the etcd-data hostPath to /var/lib/etcd-restored

IN PLAIN WORDS:
Part 1 is one long command. Part 2 is one command plus a 1-line change in etcd.yaml.

SET UP IN KILLERCODA:
rm -f /opt/etcd-backup.db ; rm -rf /var/lib/etcd-restored ; clear

SOLVE IT, STEP BY STEP:
0. Start of every question: in Killercoda just k get nodes (exam: ssh line first)
1. Step 1. Get the command from the docs
   1. Open https://kubernetes.io/docs 2. Search: etcd backup 3. Click: "Operating etcd clusters for Kubernetes"    (direct link: https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/ ) 4. Go to the heading "Backing up an etcd cluster" → "Snapshot using etcdctl options". Copy the command that has --cacert, --cert and --key.
2. Step 2. Find the three certificate paths
   $ grep -E "trusted-ca-file|cert-file|key-file" /etc/kubernetes/manifests/etcd.yaml
   Use the three lines WITHOUT the word peer:
   | 
   
    | Line in etcd.yaml
    | Flag for etcdctl
    | Usual value
   
    | --trusted-ca-file=
    | --cacert=
    | /etc/kubernetes/pki/etcd/ca.crt
   
    | --cert-file=
    | --cert=
    | /etc/kubernetes/pki/etcd/server.crt
   
    | --key-file=
    | --key=
    | /etc/kubernetes/pki/etcd/server.key
3. Step 3. Take the snapshot
   $ etcdctl snapshot save /opt/etcd-backup.db \
   $ --endpoints=https://127.0.0.1:2379 \
   $ --cacert=/etc/kubernetes/pki/etcd/ca.crt \
   $ --cert=/etc/kubernetes/pki/etcd/server.crt \
   $ --key=/etc/kubernetes/pki/etcd/server.key
   You want Snapshot saved at /opt/etcd-backup.db.
   If the question only asks for a backup, you are finished: ls -l /opt/etcd-backup.db.
4. Step 4. Restore into a new folder
   $ etcdutl snapshot restore /opt/etcd-backup.db --data-dir=/var/lib/etcd-restored
   (If etcdutl is not installed, the same line with etcdctl works.) No certificates needed: this only unpacks a file.
5. Step 5. Tell etcd to use the new folder
   $ cp /etc/kubernetes/manifests/etcd.yaml /root/etcd.yaml.bak
   $ vim /etc/kubernetes/manifests/etcd.yaml
   Press G to jump to the end of the file. You see:
   YOU SEE:   volumes:
              - hostPath:
                  path: /etc/kubernetes/pki/etcd
                  type: DirectoryOrCreate
                name: etcd-certs
              - hostPath:
                  path: /var/lib/etcd
                  type: DirectoryOrCreate
                name: etcd-data
   Change ONE line: in the block named etcd-data, change
   | 
   
    | Before
    | After
   
    | path: /var/lib/etcd
    | path: /var/lib/etcd-restored
   Save with Esc, :wq.
   Why only this line: hostPath is the folder on the machine. It is shown INSIDE the etcd container at /var/lib/etcd (that is the mountPath). etcd reads /var/lib/etcd inside the container (that is --data-dir). By changing only the hostPath, etcd keeps reading the same place, but that place now shows the restored folder. Leave --data-dir and mountPath alone.
   Check:
   YOU SEE: grep -n "etcd-restored" /etc/kubernetes/manifests/etcd.yaml
   You want exactly 1 line.
6. Closing routine
   The kubelet restarts etcd by itself. kubectl does not answer for up to 60 seconds. That is normal.
   $ k get nodes
   $ k get pods -n kube-system | grep etcd

IF SOMETHING GOES WRONG:
| 

 | You see
 | Cause
 | Fix

 | snapshot save hangs or says context deadline exceeded
 | a certificate path or the endpoint is wrong
 | compare with step 2

 | kubectl does not come back after 2 minutes
 | a typo in etcd.yaml
 | `crictl ps -a

 | data-dir ... not empty on restore
 | the target folder already exists
 | choose a new folder name or rm -rf it first

TRAPS TO AVOID:
- Using the peer-cert/peer-key files instead of server.crt/server.key
- Changing --data-dir or the mountPath instead of only the hostPath path
- Panicking when kubectl is silent for ~60 s after saving etcd.yaml

VERIFY AGAINST THE QUESTION:
- snapshot exists: $ ls -l /opt/etcd-backup.db  → must see: file, size > 0
- etcd uses restored dir: $ grep etcd-restored /etc/kubernetes/manifests/etcd.yaml  → must see: exactly 1 line
- cluster up: $ k get pods -n kube-system | grep etcd  → must see: 1/1 Running

MEMORISE (fast version, target 8 min):
docs: 'etcd backup' → Operating etcd clusters
grep -E 'trusted-ca-file|cert-file|key-file' /etc/kubernetes/manifests/etcd.yaml
etcdctl snapshot save /opt/etcd-backup.db --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key
etcdutl snapshot restore /opt/etcd-backup.db --data-dir=/var/lib/etcd-restored
vim /etc/kubernetes/manifests/etcd.yaml   # etcd-data hostPath path: /var/lib/etcd-restored


==================== PAGE 23 · NodePort ====================
EXAM QUESTION:
In namespace `web`:
1. Edit deployment `np` so that the container declares port `80` (TCP).
2. Create a Service named `np-svc` of type `NodePort` that exposes the deployment on port `80`, using node port `30080`.
WRITE DOWN: namespace = `web` · deployment = `np` · containerPort = `80` · Service = `np-svc` · port = `80` · nodePort = `30080`

WORDS YOU NEED:
- containerPort = a line in the pod template that states which port the container listens on.

- NodePort Service = a Service that also opens a port on every node. Three numbers are involved:

- port = the Service&#39;s own port

- targetPort = the container&#39;s port

- nodePort = the port on every node (30000 to 32767)

- k expose = the command that creates a Service for a Deployment. It copies the Deployment&#39;s labels into the selector, so the selector is always right.

SPOT THE PATTERN: Add containerPort, expose as NodePort with fixed nodePort
  "the container declares port `80` (TCP)" → k edit deploy: add ports: - containerPort: 80 protocol: TCP under the container
  "of type `NodePort`" → k expose … --type=NodePort
  "using node port `30080`" → k expose can't set it: k edit svc → nodePort: 30080

IN PLAIN WORDS:
Two jobs. Add two lines to the Deployment. Create a Service, then set its node port to a fixed number (Kubernetes picks a random one otherwise).

SET UP IN KILLERCODA:
k delete ns web --ignore-not-found
k create ns web
k create deploy np --image=nginx:1.27 -n web

SOLVE IT, STEP BY STEP:
0. Start of every question: in Killercoda just k get nodes (exam: ssh line first)
1. Step 1. Add the container port to the Deployment
   $ k edit deploy np -n web
   Type /image: and press Enter. You see:
   YOU SEE:       containers:
                  - image: nginx:1.27
                    imagePullPolicy: IfNotPresent
                    name: nginx
   Press o (opens a new line below) and add these two lines. ports: must start in the same column as image: / name::
   YOU SEE:         ports:
                    - containerPort: 80
   Save with Esc, :wq. You see deployment.apps/np edited.
2. Step 2. Create the Service
   $ k expose deploy np --name=np-svc --port=80 --target-port=80 --type=NodePort -n web
3. Step 3. Set the node port
   $ k edit svc np-svc -n web
   Type /nodePort and press Enter. You see a random number:
   YOU SEE:   - nodePort: 31544
                port: 80
   Change it to 30080. Save with Esc, :wq.
4. Closing routine
   $ k get svc np-svc -n web
   You want TYPE NodePort and PORT(S) 80:30080/TCP.
   $ k get endpoints np-svc -n web
   $ curl -s -m 3 node01:30080 | head -5

IF SOMETHING GOES WRONG:
| 

 | You see
 | Cause
 | Fix

 | after step 1 vim reopens with an error at the top
 | wrong indentation, or a Tab character
 | ports: lines up with name:. Spaces only.

 | the Service is called np
 | you forgot --name=np-svc
 | k delete svc np -n web, run step 2 again

 | provided port is not in the valid range
 | nodePort outside 30000 to 32767
 | use the number from the question

 | curl fails but endpoints are fine
 | you curled the wrong node name
 | k get nodes -o wide, use a node IP

TRAPS TO AVOID:
- Wrong indentation of ports: (must line up with image:)
- Leaving the random nodePort from k expose
- Forgetting -n web

VERIFY AGAINST THE QUESTION:
- container declares 80: $ k get deploy np -n web -o jsonpath='{..ports}'  → must see: containerPort 80 TCP
- service correct: $ k get svc np-svc -n web  → must see: NodePort 80:30080/TCP

==================== PAGE 24 · Ingress ====================
EXAM QUESTION:
In namespace `web`, create an Ingress named `web-ing` that uses the existing IngressClass. Requests for host `shop.example.com` with path `/` (type Prefix) must go to service `backend-svc` on port `80`.
WRITE DOWN: namespace = `web` · Ingress = `web-ing` · host = `shop.example.com` · path = `/` Prefix · Service = `backend-svc` · port = `80` · class = "the existing one" (look it up)

WORDS YOU NEED:
- Ingress = a rule for web traffic coming into the cluster: "host X, path Y → Service Z, port N".

- IngressClass = the name of the controller that will carry out the rule (for example nginx). An Ingress without a class is ignored.

- pathType: Prefix = the rule matches the path and everything below it. / with Prefix matches every request.

SPOT THE PATTERN: Create Ingress imperatively: host/path → service:port
  "uses the existing IngressClass" → k get ingressclass → --class=<name>
  "with path `/` (type Prefix)" → In --rule use /* (star = Prefix)
  "must go to service `backend-svc` on port `80`" → =backend-svc:80

IN PLAIN WORDS:
One object, and there is a command for it. No YAML.

SET UP IN KILLERCODA:
k delete ns web --ignore-not-found
k create ns web
k create deploy backend --image=nginx:1.27 -n web
k expose deploy backend --name=backend-svc --port=80 -n web
cat <<EOF | k apply -f -
apiVersion: networking.k8s.io/v1
kind: IngressClass
metadata:
  name: nginx
spec:
  controller: k8s.io/ingress-nginx
EOF

SOLVE IT, STEP BY STEP:
0. Start of every question: in Killercoda just k get nodes (exam: ssh line first)
1. Step 1. Find the class name
   $ k get ingressclass
   You see nginx. Write it down.
2. Step 2. Create the Ingress
   $ k create ingress web-ing --class=nginx --rule="shop.example.com/*=backend-svc:80" -n web
   How to read the rule: "HOST/PATH=SERVICE:PORT"
   | 
   
    | Part
    | Meaning
   
    | shop.example.com
    | the host
   
    | /*
    | path /. The * makes it pathType: Prefix. Without * it becomes Exact.
   
    | backend-svc:80
    | Service name and Service port
3. Closing routine
   $ k describe ing web-ing -n web
   You want:
   YOU SEE: Ingress Class:    nginx
            Rules:
              Host              Path  Backends
              shop.example.com  /     backend-svc:80 (192.168.x.x:80)
   The IP in brackets proves the Service name and port are right.

IF SOMETHING GOES WRONG:
| 

 | You see
 | Cause
 | Fix

 | Backends shows <error: services "..." not found>
 | the Service name or port has a typo
 | k delete ing web-ing -n web, create again

 | Ingress Class: <none>
 | you forgot --class
 | delete and create again

 | the question asks for TLS with secret web-tls
 | add it inside the rule
 | --rule="shop.example.com/*=backend-svc:80,tls=web-tls"

 | the question asks for two paths
 | repeat the flag
 | --rule="host/api*=api-svc:80" --rule="host/*=web-svc:80"

 | the question asks for an annotation (for example rewrite-target)
 | add a flag
 | --annotation nginx.ingress.kubernetes.io/rewrite-target=/

TRAPS TO AVOID:
- Writing host/ instead of host/* → creates pathType Exact
- Forgetting --class, so no controller picks it up
- Forgetting quotes around --rule

VERIFY AGAINST THE QUESTION:
- rule correct: $ k describe ing web-ing -n web  → must see: shop.example.com / backend-svc:80 (<pod IP>:80)
- class set: $ k get ing web-ing -n web  → must see: CLASS nginx

MEMORISE (fast version, target 3 min):
k get ingressclass
k create ingress web-ing --class=nginx --rule="shop.example.com/*=backend-svc:80" -n web
k describe ing web-ing -n web


==================== PAGE 25 · Gateway API (replace an Ingress) ====================
EXAM QUESTION:
In namespace `web`, an Ingress named `web-ing` exposes an application over HTTPS. Migrate it to the Gateway API:
1. Create a Gateway named `web-gw` that uses the existing GatewayClass and keeps the same hostname and TLS configuration as the Ingress.
2. Create an HTTPRoute named `web-route` that keeps the same routing rules as the Ingress.
3. Delete the Ingress.
WRITE DOWN: namespace = `web` · Gateway = `web-gw` · HTTPRoute = `web-route` · source = Ingress `web-ing`

WORDS YOU NEED:
- Gateway = the entry point: which port, which protocol, which hostname, which TLS certificate. It names a GatewayClass (the controller), the same way an Ingress names an IngressClass.

- HTTPRoute = the routing rule: which host and path go to which Service and port. It points to its Gateway with parentRefs.

- Together they do what ONE Ingress did. An Ingress → Gateway migration means: read the values out of the Ingress, write them into these two objects.

SPOT THE PATTERN: Ingress → Gateway + HTTPRoute (copy host, TLS, rules)
  "uses the existing GatewayClass" → k get gatewayclass → gatewayClassName
  "keeps the same hostname and TLS configuration as the Ingress" → Listener: protocol HTTPS, port 443, hostname, tls.certificateRefs = Ingress secretName
  "keeps the same routing rules as the Ingress" → HTTPRoute: parentRefs web-gw, hostnames, path, backendRefs service:port
  "Delete the Ingress" → k delete ing web-ing -n web — only after route is created

IN PLAIN WORDS:
The question does not give you the values. They are inside the existing Ingress. Read 5 values from it, put them into two new objects.

SET UP IN KILLERCODA:

openssl req -x509 -nodes -newkey rsa:2048 -days 30 -subj "/CN=shop.example.com" -keyout /tmp/t.key -out /tmp/t.crt 2>/dev/null
k create secret tls web-tls --cert=/tmp/t.crt --key=/tmp/t.key -n web
cat <<EOF | k apply -f -
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: nginx
spec:
  controllerName: gateway.nginx.org/nginx-gateway-controller
EOF
k create ingress web-ing --class=nginx --rule="shop.example.com/*=backend-svc:80,tls=web-tls" -n web

==================== PAGE 34 · Share a node's resources between pods ====================

WRITE DOWN: namespace = `shop` · deployment = `web` · 3 replicas · node = `node01` · 10% headroom

WORDS YOU NEED:
- Allocatable = how much CPU and memory a node offers to pods in total.

==================== PAGE 36 · Taint, toleration, nodeSelector ====================
EXAM QUESTION:

WRITE DOWN: node = `node01` · taint = `env=prod:NoSchedule` · label = `env=prod` · pod = `x`, `nginx:1.27`

WORDS YOU NEED:

- Toleration = lines in a POD that say "I accept this taint". It only ALLOWS the pod on that node. It does not send the pod there.

- nodeSelector = lines in a pod that say "only put me on a node with this label". This is what SENDS the pod to a node.

To get a pod onto a tainted node for sure, you need both: toleration (allowed) + nodeSelector (sent).

SPOT THE PATTERN: Taint + label node; pod with toleration + nodeSelector
  "Taint node `node01` with `env=prod:NoSchedule`" → k taint node node01 env=prod:NoSchedule
  "tolerates the taint" → tolerations: key env, operator Equal, value prod, effect NoSchedule

Two commands on the node. Then a pod YAML with two added blocks at pod level.

    | (empty)
    | this disk has NO class. Remember this.
   Why this step matters: you never write "use disk mariadb-pv" in a PVC. You write what you need, and Kubernetes picks a disk that matches. It compares three things: class, access mode, size. So your PVC must repeat the values you just read.
2. Step 2. Get the PVC text from the docs
   There is no k create pvc command. So you copy from the docs. Do not type it from memory.
   1. Open https://kubernetes.io/docs 2. In the search box type: persistent volume pod 3. Click the result named: "Configure a Pod to Use a PersistentVolume for Storage"    (direct link: https://kubernetes.io/docs/tutorials/configuration/configure-persistent-volume-storage/ ) 4. On the right side of the page, click the heading: "Create a PersistentVolumeClaim" 5. You see a box labelled pods/storage/pv-claim.yaml. Click the copy icon at the top of that box.
   This is what you copied:
   YOU SEE: apiVersion: v1
            kind: PersistentVolumeClaim
            metadata:
              name: task-pv-claim
            spec:
              storageClassName: manual
              accessModes:
                - ReadWriteOnce
              resources:
                requests:
                  storage: 3Gi
3. Step 3. Paste it into a file and change 4 things
   $ vim pvc.yaml
   Press i, paste, then make these 4 changes:
   | 
   
    | #
    | The docs say
    | You change it to
    | Why
   
    | 1
    | name: task-pv-claim
    | name: mariadb
    | the name the question asks for
   
    | 2
    | (no namespace line)
    | add namespace: mariadb under name:
    | the question says namespace mariadb
   
    | 3
    | storageClassName: manual
    | storageClassName: ""
    | the old disk&#39;s class is empty (step 1)
   
    | 4
    | storage: 3Gi
    | storage: 250Mi
    | the size the question asks for
   accessModes: ReadWriteOnce stays as it is. It already matches.
   The finished file:
   YOU SEE: apiVersion: v1
            kind: PersistentVolumeClaim
            metadata:
              name: mariadb
              namespace: mariadb
            spec:
              storageClassName: ""
              accessModes:
                - ReadWriteOnce
              resources:
                requests:
                  storage: 250Mi
   Press Esc, type :wq, press Enter.
   About change 3, the one people get wrong: do NOT delete the storageClassName line. If the line is missing, Kubernetes fills in the cluster&#39;s default class. That class then creates a brand-new EMPTY disk for you. Your PVC shows "Bound", everything looks fine, but the database has no data and you lose the points. Writing "" says "no class", which is exactly what the old disk has.
4. Step 4. Create the PVC and check it connected to the OLD disk
   $ k apply -f pvc.yaml
   $ k get pvc -n mariadb
   You want:
   YOU SEE: NAME      STATUS   VOLUME       CAPACITY   ACCESS MODES   STORAGECLASS   AGE
            mariadb   Bound    mariadb-pv   250Mi      RWO                           5s
   Check two columns: STATUS = Bound, and VOLUME = mariadb-pv (the old disk&#39;s name).
   The chain is now:
   YOU SEE: Pod ✗   →   PVC ✓   →   PV ✓
   If something else shows up:
   | 
   
    | You see
    | Cause
    | Fix
   
    | STATUS Pending
    | one of the three values does not match the disk
    | k describe pvc mariadb -n mariadb, read Events. Then k delete pvc mariadb -n mariadb, fix pvc.yaml, apply again.
   
    | VOLUME is a long name like pvc-3f2a...
    | you lost the storageClassName: "" line, a new empty disk was made
    | same: delete the PVC, fix the file, apply again
   (A PVC cannot be edited after creation. Delete and re-create is the normal way.)
5. Step 5. Tell the app to use the PVC
   $ vim /root/mariadb-deploy.yaml
   Type /claimName and press Enter. The cursor jumps to the line.
   | 
   
    | Before
    | After
   
    | claimName: ""
    | claimName: mariadb
   claimName is simply the NAME of the PVC you made in step 4. One word changes. Nothing else in this file is touched. Save with Esc, :wq.
6. Step 6. Start the app
   $ k apply -f /root/mariadb-deploy.yaml
7. Closing routine
   $ k get pods -n mariadb
   You want 1/1 Running. The first start can take a minute while the image downloads. Run it again if you see ContainerCreating.
   $ k get pv
   You want mariadb-pv with STATUS Bound and CLAIM mariadb/mariadb. This proves the old disk is the one in use.
   The chain is complete:
   YOU SEE: Pod ✓   →   PVC ✓   →   PV ✓

TRAPS TO AVOID:
- storageClassName mismatch → PVC Pending
- PV still Released with an old claimRef — check status before
- Forgetting namespace: mariadb in the PVC

VERIFY AGAINST THE QUESTION:
- PVC bound to old PV: $ k get pvc -n mariadb  → must see: mariadb Bound <old PV name>
- deployment running: $ k get pods -n mariadb  → must see: 1/1 Running
