

==================== PAGE 1 · ImagePullBackOff ====================
[A folded box "New here? The basics" on every page explains: k=kubectl (alias k=kubectl if missing), pod, deployment, node, namespace (-n), service, label, <placeholders>, Tab completion, vim keys i/Esc/:wq/:q!/dd/u/:set paste, sudo -i for node tasks in the real exam, YAML spacing.]
EXAM QUESTION:
In namespace `app`, the pod of deployment `api` is not Running. Find the cause and fix it so the pod reaches Running. Do not delete the deployment.
WRITE DOWN: namespace = `app` · deployment = `api` · do NOT delete the deployment

IN PLAIN WORDS:
Something stops the pod from starting. You do not know what yet. Kubernetes knows, and wrote it into the pod's Events. Read it, then fix it in the deployment.

WORDS YOU NEED:
- Image = the packaged app, stored in a registry. Written as name:tag, for example nginx:1.27. The tag is the version.

- Deployment = the object that creates and re-creates the pod. It is the pod's owner.

- ImagePullBackOff = the node tried to download the image, failed, and now waits longer and longer between retries. ErrImagePull = the same problem on the first try; you may see either.

- Pod = the smallest thing Kubernetes runs: one or more containers together. Node = a machine that runs pods. Namespace = a named folder that groups objects; most commands need -n <namespace>.

- k = short for kubectl (an alias the exam and Killercoda already set up).

SPOT THE PATTERN: Pod not Running → read Events → fix the owner (Deployment)
  "is not Running" → Look at STATUS, then read Events with describe
  "Do not delete the deployment" → Fix it in place: k set image / k edit deploy
  "so the pod reaches Running" → Done only when the NEW pod shows 1/1 Running

WATCH OUT:
- Using the deployment name (api) as the container name in set image — the container is nginx
- Forgetting -n app → 'No resources found'
- Fixing the pod instead of the deployment — the deployment recreates the broken pod

SET UP IN KILLERCODA, THEN TRY IT YOURSELF:
k delete ns app --ignore-not-found
k create ns app
k create deploy api --image=nginx:doesnotexist -n app
sleep 20   # wait 20 s for the pull to fail

SOLUTION, STEP BY STEP:
0. Start: in Killercoda just k get nodes (real exam: the ssh line from the question first)
1. Step 1. See the status
   COMMAND: k get pods -n app
   You see:
   YOU SEE:
      NAME                   READY   STATUS             RESTARTS   AGE
      api-697db8cc78-hgvdr   0/1     ImagePullBackOff   0          60s
   | 
   
    | Column
    | Value
    | Meaning
   
    | READY
    | 0/1
    | the pod should have 1 container; 0 are ready
   
    | STATUS
    | ImagePullBackOff
    | the image cannot be downloaded
   
    | RESTARTS
    | 0
    | the container never started, so nothing restarted
   If STATUS says ErrImagePull instead, it is the same problem (first try). Carry on.
   Copy the pod name.
2. Step 2. Ask Kubernetes why
   COMMAND: k describe pod <pod-name> -n app
   Read two places:
   1. Near the top, under Containers: the first indented word is the container name. Here: nginx. Write it down. 2. At the bottom, under Events: you see Failed to pull image "nginx:doesnotexist" ... not found.
   Cause found: the image nginx exists, but the tag doesnotexist does not.
3. Step 3. Fix the image in the deployment
   COMMAND: k set image deploy/api nginx=nginx:1.27 -n app
   How to read it: k set image deploy/<deployment> <container-name>=<new-image>. The left side of = is the CONTAINER name from step 2, not the deployment name.
   If the question does not give a tag, use the plain image name: nginx=nginx.
4. Closing routine
   COMMAND: k rollout status deploy/api -n app
   COMMAND: k get pods -n app
   rollout status waits until the new pod is ready, then prints successfully rolled out and returns. You want a pod with a NEW name showing 1/1 Running. The new name is correct: the deployment replaced the broken pod.
✓ End: in Killercoda nothing; real exam: exit

VERIFY AGAINST THE QUESTION:
- pod reaches Running: COMMAND k get pods -n app  → must see: new api-… pod 1/1 Running
- deployment not deleted: COMMAND k get deploy api -n app  → must see: api 1/1

IF SOMETHING GOES WRONG:
| 

 | You see
 | Cause
 | Fix

 | error: unable to find container named "api"
 | you used the deployment name on the left of =
 | use the container name from describe

 | still ImagePullBackOff
 | the new image name or tag also has a typo
 | k describe pod again, read Events, run set image again

 | No resources found
 | you forgot -n app
 | add it

MEMORISE (target 2 min):
k get pods -n app
k describe pod <pod> -n app   # Events: ImagePullBackOff, bad tag
k set image deploy/api nginx=nginx:1.27 -n app
k rollout status deploy/api -n app


==================== PAGE 2 · CrashLoopBackOff ====================
[A folded box "New here? The basics" on every page explains: k=kubectl (alias k=kubectl if missing), pod, deployment, node, namespace (-n), service, label, <placeholders>, Tab completion, vim keys i/Esc/:wq/:q!/dd/u/:set paste, sudo -i for node tasks in the real exam, YAML spacing.]
EXAM QUESTION:
In namespace `app`, the pod of deployment `api` keeps restarting. Find the cause and fix it so the pod stays Running. Do not delete the deployment. The container should run `sleep 3600`.
WRITE DOWN: namespace = `app` · deployment = `api` · correct command = `sleep 3600`

IN PLAIN WORDS:
The container starts and stops in a loop. Find out WHY it stops. The reason is in one of two places: what the container printed before it stopped (logs), or the command it was told to run (describe).

WORDS YOU NEED:
- Command = what the container runs when it starts. A container lives only as long as its command keeps running.

- Exit code = the number a command returns when it stops. 0 = finished OK. Anything else = stopped with an error.

- CrashLoopBackOff = the image downloaded fine, the container started, then stopped. Kubernetes restarts it, it stops again. Kubernetes waits longer between each retry.

SPOT THE PATTERN: Pod CrashLoopBackOff → logs --previous → fix command in Deployment
  "keeps restarting" → CrashLoopBackOff: the container starts then exits; read logs --previous
  "Do not delete the deployment" → Fix the pod template with k edit deploy
  "The container should run" → The command in the spec is wrong; set it to sleep 3600

WATCH OUT:
- Reading k logs without --previous (the new container may have no output yet)
- Editing the pod instead of the deployment
- Breaking YAML indentation in the command list

SET UP IN KILLERCODA, THEN TRY IT YOURSELF:
k delete ns app --ignore-not-found
k create ns app
k create deploy api --image=busybox:1.36 -n app -- sh -c "exit 1"

SOLUTION, STEP BY STEP:
0. Start: in Killercoda just k get nodes (real exam: the ssh line from the question first)
1. Step 1. See the status
   COMMAND: k get pods -n app
   You see (after ~30 s; in the first seconds STATUS may say Error with RESTARTS 1 — wait and run it again):
   YOU SEE:
      NAME                   READY   STATUS             RESTARTS      AGE
      api-5d9c7b6f4-x2x9k    0/1     CrashLoopBackOff   3 (20s ago)   70s
   RESTARTS is going UP. That is the difference from question 1: the container does start, then stops.
2. Step 2. Read what the stopped container printed
   COMMAND: k logs <pod-name> -n app --previous
   --previous = show the output of the container that just stopped, not the new one.
   Here it prints nothing, because exit 1 prints nothing. In the exam you often see a real message here, for example file not found or missing variable. That message is the cause.
3. Step 3. Read the command and the exit code
   COMMAND: k describe pod <pod-name> -n app
   Find these lines:
   YOU SEE:
          Command:
            sh
            -c
            exit 1
          Last State:     Terminated
            Reason:       Error
            Exit Code:    1
   Cause found: the command is exit 1. It stops at once with an error.
4. Step 4. Fix the command in the deployment
   COMMAND: k edit deploy api -n app
   This opens the deployment in vim. Type /exit 1 and press Enter. The cursor jumps onto the word exit in the line - exit 1:
   FILE CONTENT (YAML):
            - command:
              - sh
              - -c
              - exit 1        <- cursor is on the "e" of exit
   Vim keys, exactly: press C (capital C = delete from the cursor to the end of the line and start typing), type sleep 3600, press Esc, type :wq, press Enter. The line must now read - sleep 3600.
   No-vim alternative (one line, same result):
   FILE CONTENT (YAML):
      k patch deploy api -n app --type=json -p='[{"op":"replace","path":"/spec/template/spec/containers/0/command","value":["sh","-c","sleep 3600"]}]'
   You see deployment.apps/api edited.
5. Closing routine
   COMMAND: k get pods -n app
   You want 1/1 Running and RESTARTS 0. Wait 20 seconds and run it again: RESTARTS must stay 0.
✓ End: in Killercoda nothing; real exam: exit

VERIFY AGAINST THE QUESTION:
- pod stays Running: COMMAND k get pods -n app  → must see: 1/1 Running, RESTARTS stays 0 for the new pod
- container runs sleep 3600: COMMAND k get deploy api -n app -o yaml | grep -A3 command  → must see: sleep 3600

IF SOMETHING GOES WRONG:
The steps are identical. Only the message and the fix change.

 | 

 | What you read in steps 2 and 3
 | Cause
 | Fix

 | Reason: OOMKilled
 | the memory limit is too small
 | k set resources deploy api -n app --limits=memory=<value the question gives> (e.g. 256Mi)

 | STATUS CreateContainerConfigError (not a restart loop: the container never starts), Events: configmap "x" not found
 | the ConfigMap or Secret does not exist
 | create it (k create cm x --from-literal=KEY=VALUE -n app) or fix its name with k edit deploy

 | Events: Liveness probe failed
 | the probe checks the wrong port or path
 | k edit deploy api -n app, fix the port under livenessProbe:

 | logs show an error about a wrong argument
 | bad args:
 | k edit deploy api -n app, fix args:

MEMORISE (target 3 min):
k get pods -n app
k logs <pod> -n app --previous
k describe pod <pod> -n app
k edit deploy api -n app   # exit 1 → sleep 3600
k get pods -n app


==================== PAGE 3 · Pending pod ====================
[A folded box "New here? The basics" on every page explains: k=kubectl (alias k=kubectl if missing), pod, deployment, node, namespace (-n), service, label, <placeholders>, Tab completion, vim keys i/Esc/:wq/:q!/dd/u/:set paste, sudo -i for node tasks in the real exam, YAML spacing.]
EXAM QUESTION:
In namespace `app`, a pod of deployment `api` is stuck in Pending. Find the cause and fix it. The container needs `100m` CPU.
WRITE DOWN: namespace = `app` · deployment = `api` · correct CPU request = `100m`

IN PLAIN WORDS:
The scheduler looked at every node and said no to all of them. It wrote its reason into the pod's Events. Read the reason, remove the obstacle.

WORDS YOU NEED:
- Scheduler = the part of Kubernetes that picks a node for each new pod.

- Pending = the pod exists, but no node has accepted it yet.

- Request = how much CPU and memory a pod reserves. CPU is written in millicores: 1000m = 1 CPU, 100m = one tenth of a CPU. A plain 100 means 100 whole CPUs.

- Taint = a "keep out" mark on a node. Only pods with a matching toleration may run there. The controlplane usually has one, so normal pods go to node01.

SPOT THE PATTERN: Pod Pending → describe Events → lower resource requests
  "stuck in Pending" → The scheduler cannot place it: read Events (Insufficient cpu; a control-plane taint line may appear too, counts vary)
  "The container needs" → Set the CPU request to exactly 100m on the deployment

WATCH OUT:
- Setting --limits instead of --requests
- Editing the pod instead of deployment api
- Running the closing check too early — wait until the Pending pod is gone (the deployment replaces it), then the new pod shows 1/1 Running

SET UP IN KILLERCODA, THEN TRY IT YOURSELF:
k delete ns app --ignore-not-found
k create ns app
k create deploy api --image=nginx:1.27 -n app
k set resources deploy api -n app --requests=cpu=100

SOLUTION, STEP BY STEP:
0. Start: in Killercoda just k get nodes (real exam: the ssh line from the question first)
1. Step 1. See the status
   COMMAND: k get pods -n app
   You see one pod Pending. You may also see an older pod still Running: the deployment keeps the old pod until the new one works. Copy the name of the PENDING pod.
2. Step 2. Read the scheduler's reason
   COMMAND: k describe pod <pending-pod-name> -n app
   At the bottom, under Events:
   YOU SEE:
      Warning  FailedScheduling  ...  0/2 nodes are available: 1 Insufficient cpu, 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }. preemption: ...
   How to read it: "0 of 2 nodes can take this pod. One (node01) does not have enough CPU. The other (controlplane) is reserved for control-plane pods by a taint." The counts vary: if your controlplane has no taint, you see 0/2 nodes are available: 2 Insufficient cpu. The word that matters is Insufficient cpu. Ignore the preemption: part.
   Look higher up in the same output, under Requests: → cpu: 100. That is 100 whole CPUs. No node has that.
3. Step 3. Fix the request in the deployment
   COMMAND: k set resources deploy api -n app --requests=cpu=100m
4. Closing routine
   COMMAND: k get pods -n app
   You want 1/1 Running, and no Pending pod left. The Pending pod disappears on its own (the deployment replaces it); if you still see it, wait 10 s and run the command again.
✓ End: in Killercoda nothing; real exam: exit

VERIFY AGAINST THE QUESTION:
- pod no longer Pending: COMMAND k get pods -n app  → must see: new pod 1/1 Running
- request is 100m: COMMAND k get deploy api -n app -o jsonpath='{..resources}'  → must see: "requests":{"cpu":"100m"}

IF SOMETHING GOES WRONG:
The Events line always names the cause. Match it:

 | 

 | Events says
 | Cause
 | Fix

 | Insufficient cpu or Insufficient memory
 | the request is too big
 | k set resources deploy api -n app --requests=cpu=100m,memory=128Mi

 | had untolerated taint {key: value}
 | the node has a taint the pod does not tolerate
 | remove the taint: k taint node node01 key=value:NoSchedule- (or add a toleration, question 36 "Taint, toleration, nodeSelector")

 | didn't match Pod's node affinity/selector
 | the pod asks for a node label that no node has
 | k edit deploy api -n app and fix nodeSelector:, or k label node node01 key=value

 | unbound immediate PersistentVolumeClaims
 | its PVC is not Bound
 | fix the PVC (questions 38 "PV + PVC + Pod" and 40 "Reuse an existing PV")

 | Events is empty (<none>) and Node: <none>
 | the scheduler itself is not running
 | question 9 "Scheduler is not running"

MEMORISE (target 2 min):
k get pods -n app
k describe pod <pod> -n app   # Insufficient cpu
k set resources deploy api -n app --requests=cpu=100m
k get pods -n app


==================== PAGE 4 · Node NotReady: kubelet stopped ====================
[A folded box "New here? The basics" on every page explains: k=kubectl (alias k=kubectl if missing), pod, deployment, node, namespace (-n), service, label, <placeholders>, Tab completion, vim keys i/Esc/:wq/:q!/dd/u/:set paste, sudo -i for node tasks in the real exam, YAML spacing.]
EXAM QUESTION:
Node `node01` is in state NotReady. Find the cause and bring the node back to Ready. The fix must survive a reboot. Do not reboot the node.
WRITE DOWN: node = `node01` · must survive reboot (so: `enable`) · no reboot

IN PLAIN WORDS:
The kubelet on node01 is not reporting. Log in to node01, check the kubelet service, start it.

WORDS YOU NEED:
- kubelet = a program that runs on every node. It starts the containers, and every few seconds it reports "this node is alive" to the control plane.

- NotReady = the control plane has not heard from that node's kubelet for about 40 seconds.

- systemctl = the Linux command that starts, stops and checks services. kubelet is a Linux service, not a pod. So kubectl cannot start it. You must log in to the node.

SPOT THE PATTERN: Node NotReady → ssh → kubelet stopped → enable --now
  "is in state NotReady" → Kubelet on that node is not reporting: ssh in and check systemctl
  "The fix must survive a reboot" → Use systemctl enable (not only start)
  "Do not reboot the node" → Start the service by hand: enable --now

WATCH OUT:
- systemctl start only — kubelet stays disabled, lost after reboot (check: systemctl is-enabled kubelet → enabled)
- Running systemctl on the control plane instead of node01 — the prompt must say node01 before you type
- Forgetting to exit back before k get nodes

SET UP IN KILLERCODA, THEN TRY IT YOURSELF:
ssh node01 "systemctl disable --now kubelet"

SOLUTION, STEP BY STEP:
0. Start: in Killercoda just k get nodes (real exam: the ssh line from the question first)
1. Step 1. Get the hint from the control plane
   COMMAND: k describe node node01
   Find the Conditions: table. You see Unknown and the message Kubelet stopped posting node status.
   That sentence tells you: the problem is the kubelet, on that node.
2. Step 2. Log in to the node
   COMMAND: ssh node01
   The prompt changes to root@node01. Always look at the prompt before you type.
3. Step 3. Check the kubelet service
   COMMAND: systemctl status kubelet
   You see:
   FILE CONTENT (YAML):
           Loaded: loaded (/usr/lib/systemd/system/kubelet.service; disabled; ...)
           Active: inactive (dead) since ...
   inactive (dead) = the service is stopped. disabled = it will not start after a reboot either. If the screen does not return to the prompt, press q.
4. Step 4. Start it
   COMMAND: systemctl enable --now kubelet
   - --now = start it immediately - enable = also start it after every reboot (the question asked for this)
   Check:
   COMMAND: systemctl status kubelet
   COMMAND: systemctl is-enabled kubelet
   You want Active: active (running) (press q), and is-enabled prints enabled (= survives a reboot).
5. Step 5. Leave the node
   COMMAND: exit
   The prompt is root@controlplane again.
6. Closing routine
   COMMAND: k get nodes
   You want node01   Ready. It can take 30 seconds. Run it again if needed.
✓ End: in Killercoda nothing; real exam: exit

VERIFY AGAINST THE QUESTION:
- node Ready: COMMAND k get nodes  → must see: node01 Ready
- survives reboot: COMMAND ssh node01 systemctl is-enabled kubelet  → must see: enabled

IF SOMETHING GOES WRONG:
| 

 | You see
 | Cause
 | Fix

 | The connection to the server localhost:8080 was refused
 | you ran kubectl ON node01. kubectl is only set up on the control plane.
 | type exit, run it again

 | kubelet is already active (running) before you fixed anything
 | you ran systemctl on the control plane, not node01
 | look at the prompt: it must say node01. exit, then ssh node01

 | after starting: Active: activating (auto-restart)
 | the kubelet is misconfigured, not just stopped
 | question 5

 | kubelet is active (running) but the node stays NotReady
 | the container runtime is stopped
 | on the node: systemctl enable --now containerd

MEMORISE (target 2 min):
k describe node node01   # Kubelet stopped posting status
ssh node01
systemctl status kubelet
systemctl enable --now kubelet
exit; k get nodes


==================== PAGE 5 · Node NotReady: kubelet misconfigured ====================
[A folded box "New here? The basics" on every page explains: k=kubectl (alias k=kubectl if missing), pod, deployment, node, namespace (-n), service, label, <placeholders>, Tab completion, vim keys i/Esc/:wq/:q!/dd/u/:set paste, sudo -i for node tasks in the real exam, YAML spacing.]
EXAM QUESTION:
Node `node01` is in state NotReady. Find the cause and bring the node back to Ready. Do not reboot the node.
WRITE DOWN: node = `node01` · no reboot

IN PLAIN WORDS:
The wording is the same as question 4. You only find out on the node that this one is harder: the kubelet is not just stopped, it cannot start. Something in its configuration is wrong. journalctl tells you what.

WORDS YOU NEED:
- Service file = a text file that tells Linux how to start a service. The line ExecStart= holds the path of the program to run.

- journalctl = the command that shows a service's log. It tells you WHY a service fails.

- daemon-reload = tells Linux "I changed a service file, read it again". Without it, Linux keeps using the old version.

SPOT THE PATTERN: Node NotReady → kubelet fails → fix service file path
  "is in state NotReady" → ssh to node01, check kubelet status and journal
  "Do not reboot the node" → After editing the service file: daemon-reload + restart kubelet

WATCH OUT:
- Forgetting systemctl daemon-reload after editing the service file
- Editing the wrong block — systemctl cat kubelet shows two ExecStart blocks; edit the one whose path contains local (the drop-in 10-kubeadm.conf)
- Only starting kubelet without fixing the bad /usr/local/bin path

SET UP IN KILLERCODA, THEN TRY IT YOURSELF:
ssh node01 'f=$(ls /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf /etc/systemd/system/kubelet.service.d/10-kubeadm.conf 2>/dev/null | head -1); echo "drop-in: $f"; sed -i "s#/usr/bin/kubelet#/usr/local/bin/kubelet#" "$f" && grep -n local "$f"; systemctl daemon-reload; systemctl restart kubelet'

SOLUTION, STEP BY STEP:
0. Start: in Killercoda just k get nodes (real exam: the ssh line from the question first)
1. Step 1. Log in to the node and check the service
   COMMAND: ssh node01
   COMMAND: systemctl status kubelet
   You see:
   FILE CONTENT (YAML):
           Active: activating (auto-restart) (Result: exit-code)
          Process: ... ExecStart=/usr/local/bin/kubelet ... (code=exited, status=203/EXEC)
   | 
   
    | You see
    | Meaning
   
    | inactive (dead)
    | just stopped → question 4
   
    | activating (auto-restart)
    | tries to start, fails, tries again → it is misconfigured → this question
   Press q.
2. Step 2. Read WHY it fails
   COMMAND: journalctl -u kubelet -n 30 --no-pager
   - -u kubelet = only this service - -n 30 = the last 30 lines - --no-pager = print it, do not open a viewer
   You see:
   YOU SEE:
      kubelet.service: Failed to locate executable /usr/local/bin/kubelet: No such file or directory
   Cause found: the service file points to a program path that does not exist.
3. Step 3. Find the correct path
   COMMAND: which kubelet
   Answer: /usr/bin/kubelet
4. Step 4. Find which file holds the wrong path
   COMMAND: systemctl cat kubelet
   It prints every file of the service, each with its path in a # line on top. You see TWO blocks with ExecStart=: - # /usr/lib/systemd/system/kubelet.service with ExecStart=/usr/bin/kubelet (the base file; the drop-in overrides it, leave it alone); - the drop-in, with an empty ExecStart= (that only clears the old value; normal) followed by ExecStart=/usr/local/bin/kubelet ....
   Edit the block whose ExecStart= contains local. The # line above it names the file:
   FILE CONTENT (YAML):
      # /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf
   (Some installs keep it in /etc/systemd/system/kubelet.service.d/10-kubeadm.conf. Use whatever path YOUR output shows.)
5. Step 5. Fix the file
   COMMAND: vim /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf
   Vim keys, exactly: type /local and press Enter (the cursor lands on the l of local). Type 6x (deletes 6 characters: local/). The line now reads ExecStart=/usr/bin/kubelet .... Type :wq and press Enter (you never entered insert mode, so no Esc is needed; pressing it anyway does no harm).
6. Step 6. Reload, restart, check
   COMMAND: systemctl daemon-reload
   COMMAND: systemctl restart kubelet
   COMMAND: systemctl status kubelet
   You want Active: active (running). Press q.
7. Step 7. Leave the node
   COMMAND: exit
8. Closing routine
   COMMAND: k get nodes
   You want node01   Ready (up to 30 seconds).
✓ End: in Killercoda nothing; real exam: exit

VERIFY AGAINST THE QUESTION:
- kubelet running: COMMAND systemctl status kubelet  → must see: Active: active (running)
- node Ready: COMMAND k get nodes  → must see: node01 Ready

IF SOMETHING GOES WRONG:
journalctl always names the problem. These are the files where the fix goes:

 | 

 | journalctl says
 | File to fix
 | Then

 | Failed to locate executable ...
 | /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf (the ExecStart= line)
 | daemon-reload + restart

 | unknown flag: --xyz
 | /var/lib/kubelet/kubeadm-flags.env
 | restart

 | failed to load kubelet config file or unable to load client CA file ...
 | /var/lib/kubelet/config.yaml (correct CA path: /etc/kubernetes/pki/ca.crt)
 | restart

 | dial tcp ...:6553: connection refused (wrong API server port)
 | /etc/kubernetes/kubelet.conf (correct port: 6443)
 | restart

daemon-reload is only needed after changing a service file (under /usr/lib/systemd/ or /etc/systemd/). Running it when not needed does no harm.

MEMORISE (target 4 min):
ssh node01; systemctl status kubelet
journalctl -u kubelet -n 30 --no-pager
which kubelet; systemctl cat kubelet
vim /usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf   # /usr/local/bin/kubelet → /usr/bin/kubelet
systemctl daemon-reload; systemctl restart kubelet


==================== PAGE 6 · Service has no endpoints ====================
[A folded box "New here? The basics" on every page explains: k=kubectl (alias k=kubectl if missing), pod, deployment, node, namespace (-n), service, label, <placeholders>, Tab completion, vim keys i/Esc/:wq/:q!/dd/u/:set paste, sudo -i for node tasks in the real exam, YAML spacing.]
EXAM QUESTION:
In namespace `web`, pod `client` cannot reach service `backend-svc` on port 80. The deployment `backend` is Running. Find and fix the issue. Do not delete or recreate the service.
WRITE DOWN: namespace = `web` · service = `backend-svc` · deployment = `backend` · test pod = `client` · do NOT recreate the service

IN PLAIN WORDS:
The pods are healthy. The Service exists. But the Service is not connected to the pods. Compare the Service's selector with the pods' labels.

WORDS YOU NEED:
- Label = a key=value tag on an object, for example app=backend.

- Selector = a label written inside a Service. The Service sends traffic to every pod that carries that label.

- Endpoints = the list of pod IPs the Service found with its selector. Empty list = the Service found no pods = traffic goes nowhere.

SPOT THE PATTERN: Service unreachable → no endpoints → fix selector to match labels
  "cannot reach service" → Check k get endpoints first: empty = selector mismatch
  "is Running" → Pods are fine; the Service is the problem
  "Do not delete or recreate the service" → Change it in place: k set selector or k edit svc

WATCH OUT:
- Relabelling the pods instead of fixing the service selector
- Copying the pod-template-hash label into the selector — the hash changes on every rollout, so the Service loses its pods again

IN PLAIN WORDS:
Do the same routine twice: first on the control plane, then on the worker. Only ONE command differs: kubeadm upgrade apply v1.35.2 on the control plane, kubeadm upgrade node on the worker. Drain and uncordon always run on the control plane.

WORDS YOU NEED:
- kubeadm = the tool that installed the cluster. It also upgrades it.

- Three programs are upgraded on each machine: kubeadm (the tool), kubelet (the node agent), kubectl (the command line).

- drain / uncordon = drain moves the pods off a node and closes it for new pods. uncordon opens it again. You drain before the upgrade and uncordon after. Both are kubectl commands, so you run them on the control plane.

- apt-get / apt-mark hold = apt-get is the Ubuntu package installer. apt-mark hold locks a package so it is never updated by accident. You unlock (unhold), install, lock again.

- Version numbers = 1.35.2 means minor 35, patch 2. The apt package text adds a suffix, for example 1.35.2-1.1. A new MINOR version (1.34 → 1.35) also needs a one-word change in the apt source file; a new patch (1.35.0 → 1.35.2) does not.

- ssh node01 = log in to the worker machine. exit brings you back to the control plane.

Do not memorise the commands. Follow the docs page line by line. Memorise only the order:

Copydrain → apt-get update → new kubeadm → kubeadm upgrade → new kubelet + kubectl → restart kubelet → uncordon

  "Upgrade the control plane node to Kubernetes `1.35.2`" → Control plane first: kubeadm upgrade apply v1.35.2

  "Drain each node before upgrading it and make it schedulable again afterwards" → k drain … --ignore-daemonsets before, k uncordon after

- Running k drain/uncordon on node01 (no kubeconfig there) — exit back to the control plane first

EXAM QUESTION:
In namespace `web`, an Ingress named `web-ing` exposes an application over HTTPS. Migrate it to the Gateway API:
1. Create a Gateway named `web-gw` that uses the existing GatewayClass and keeps the same hostname and TLS configuration as the Ingress.
2. Create an HTTPRoute named `web-route` that keeps the same routing rules as the Ingress.
3. Delete the Ingress.
WRITE DOWN: namespace = `web` · Gateway = `web-gw` · HTTPRoute = `web-route` · source = Ingress `web-ing`

IN PLAIN WORDS:
The question does not give you the values. They are inside the existing Ingress. Read 5 values from it, put them into two new objects.

WORDS YOU NEED:
- Gateway = the entry point: which port, which protocol, which hostname, which TLS certificate. It names a GatewayClass (the controller), the same way an Ingress names an IngressClass.

- HTTPRoute = the routing rule: which host and path go to which Service and port. It points to its Gateway with parentRefs.

- Together they do what ONE Ingress did. An Ingress → Gateway migration means: read the values out of the Ingress, write them into these two objects.

- Path types have new names: Ingress pathType: Prefix = HTTPRoute type: PathPrefix. Ingress Exact = HTTPRoute Exact.

SPOT THE PATTERN: Ingress → Gateway + HTTPRoute (copy host, TLS, rules)
  "uses the existing GatewayClass" → k get gatewayclass → gatewayClassName

- Not restarting the deployment — old config stays in nginx
- Deleting the trailing ; → nginx fails to start
- Editing the deployment instead of the ConfigMap

Add three things to the Deployment:

Copy1. a volume                          (pod level)
2. a mount of it in the main container   (container level)
3. the sidecar, which also mounts it     (pod level, under initContainers)

WORDS YOU NEED:
- Sidecar = a second container in the same pod that helps the main one (for example: reads its log file). In YAML it is written under initContainers: with restartPolicy: Always. That one line is what makes it a sidecar: it starts first and keeps running.

- emptyDir volume = an empty folder that belongs to the pod. Every container in the pod that mounts it sees the same files.

- volumeMounts = where a volume appears inside a container. Two containers in one pod do NOT see each other's files unless both mount the same volume.

SPOT THE PATTERN: Add native sidecar (initContainer, restartPolicy Always) + shared emptyDir

  "Use a shared volume named `logs` mounted at `/var/log` in both containers" → volumes: - name: logs emptyDir: {} + volumeMounts in BOTH containers
  "Do not change the existing container's image or command" → Only add volumeMounts to the main container

WATCH OUT:
- Mounting the volume only in the sidecar — the main app writes to its own /var/log
- Putting volumes: under the container instead of at pod spec level
- Forgetting restartPolicy: Always → it becomes a normal init container that blocks forever

EXAM QUESTION:

WRITE DOWN: namespace = `shop` · deployment = `web` · 3 replicas · node = `node01` · 10% headroom

IN PLAIN WORDS:
A calculation, then one command:

Copy(allocatable − already requested) × 0.9 ÷ 3  =  request per pod

WORDS YOU NEED:
- Allocatable = how much CPU and memory a node offers to pods in total.

- Allocated (requests) = how much of that is already reserved by the pods running there.

- Request = what one pod reserves. The scheduler only places a pod on a node if allocatable − already requested ≥ the pod's request. Ask for too much and the pod stays Pending.

SPOT THE PATTERN: Compute requests from node allocatable, split across replicas
  "share the node's available resources equally" → (allocatable − already requested by others) ÷ 3
  "Leave roughly 10% headroom" → Multiply the free amount by 0.9, round down
  "All 3 pods must be Running afterwards" → Scale to 0 first, set requests, scale back to 3 and check

WATCH OUT:
- Using Capacity instead of Allocatable
- Counting web's own current requests as used (scale to 0 first)
- Setting limits instead of requests

1. Taint node `node01` with `env=prod:NoSchedule`.
2. Label node `node01` with `env=prod`.
3. Create a pod named `x` with image `nginx:1.27` in namespace `default` that tolerates the taint and is scheduled on `node01`.
WRITE DOWN: node = `node01` · taint = `env=prod:NoSchedule` · label = `env=prod` · pod = `x`, `nginx:1.27`

IN PLAIN WORDS:
Two commands on the node. Then a pod YAML with two added blocks at pod level.

WORDS YOU NEED:
- Taint = a mark on a NODE, written key=value:effect. With effect NoSchedule, the scheduler puts no new pod on that node, unless the pod tolerates the taint.

- Toleration = lines in a POD that say "I accept this taint". It only ALLOWS the pod on that node. It does not send the pod there.

- nodeSelector = lines in a pod that say "only put me on a node with this label". This is what SENDS the pod to a node.

To get a pod onto a tainted node for sure, you need both: toleration (allowed) + nodeSelector (sent).

SPOT THE PATTERN: Taint + label node; pod with toleration + nodeSelector
  "Taint node `node01` with `env=prod:NoSchedule`" → k taint node node01 env=prod:NoSchedule
  "tolerates the taint" → tolerations: key env, operator Equal, value prod, effect NoSchedule
  "is scheduled on `node01`" → nodeSelector: env: prod (a toleration alone doesn't force placement)

WATCH OUT:
- Only adding the toleration — pod may land on another node
- Putting tolerations under the container
- Typo in effect (NoSchedule is case-sensitive)
